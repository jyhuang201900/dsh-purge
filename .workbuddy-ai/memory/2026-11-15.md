## 1.1.116 — 排名表兜底把「未知」当「最差」（`103c7af`，tag `v1.1.116-rank`）

### 真缺陷：坏结果被成功覆盖
`REVERT_RANK` 只登记 3 个键（missing/absent/reverted），但实际状态还有
`applied` / `failed` / `na` / `skipped`。`RANK[x] ?? 0` 把未登记状态当成 missing（最小 0）：
- `worseRevertHit('failed','applied')` = **'applied'**（坏结果被成功覆盖）
- `worseRevertHit('applied','missing')` = 'missing'（成功被"缺文件"覆盖）

**而该函数注释正写着「坏结果不被成功覆盖」—— 兜底值把承诺反着做了。**

修：每个真实状态显式排名（applied/skipped/na=0, missing=1, absent=2, reverted=3, failed=4），
未知值 `UNKNOWN_RANK=99` **浮到最高**。

### 这是**复发型**缺陷
`APPLY_STATUS_RANK`（core.js L1980）早就修过同一问题（用 `__unknown=-1`），注释写得极清楚。
→ **同一个文件里第二次出现**说明这类错会反复犯，必须闸门守，不能靠记性。

### 第 32 关 INSERT 列完整性
判据：表有列 + 代码收参数 + INSERT 漏写 → 值永远 null（1.1.115 的 stage_code）。
**真值来源必须用真实库 PRAGMA，不能解析 DDL 文本**：
正则 `CREATE TABLE ... \n\);` 会被表体注释截断，把已有列误报成缺失
（`asset.primary_name` 就这样），真问题反而埋进噪音里。
审计要点：INSERT 写了表里不存在的列 = 硬缺陷；回读值必须 == 入参。

### 第 33 关 枚举兜底语义
行为断言 5 条 + 静态扫 `RANK[...] ?? 0`。
**静态扫必须先整文件剥块注释再逐行**：逐行剥漏掉多行块注释的中间行，
会把"讲解坑的注释"当成坑本身报红 —— 闸门自己制造噪音。

### 探针结论（这些没问题，别再怀疑）
- 库损坏（DROP TABLE asset）→ `listAssets`/`stageProgress` 正确抛 `no such table: asset`，不静默返回空。
- 非法靶标 id → 抛 `engagement not found`；工具层给「没有靶标 X｜现有：…」而非空列表。
