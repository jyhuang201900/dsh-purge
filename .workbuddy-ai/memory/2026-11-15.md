## 1.1.116 — 排名表兜底把「未知」当「最差」（`103c7af`，tag `v1.1.116-rank`）

### 真缺陷：坏结果被成功覆盖
`REVERT_RANK` 只登记 3 个键（missing/absent/reverted），但实际状态还有
`applied` / `failed` / `na` / `skipped`。`RANK[x] ?? 0` 把未登记状态当成 missing（最小 0）：
- `worseRevertHit('failed','applied')` = **'applied'**（坏结果被成功覆盖）
- `worseRevertHit('applied','missing')` = 'missing'（成功被"缺文件"覆盖）

**而该函数注释正写着「坏结果不被成功覆盖」—— 兜底值把承诺反着做了。**

修：每个真实状态显式排名（applied/skipped/na=0, missing=1, absent=2, reverted=3, failed=4），
未知值 `UNKNOWN_RANK=99` **浮到最高**。

### 这是**复发型**缺陷
`APPLY_STATUS_RANK`（core.js L1980）早就修过同一问题（用 `__unknown=-1`），注释写得极清楚。
→ **同一个文件里第二次出现**说明这类错会反复犯，必须闸门守，不能靠记性。

### 第 32 关 INSERT 列完整性
判据：表有列 + 代码收参数 + INSERT 漏写 → 值永远 null（1.1.115 的 stage_code）。
**真值来源必须用真实库 PRAGMA，不能解析 DDL 文本**：
正则 `CREATE TABLE ... \n\);` 会被表体注释截断，把已有列误报成缺失
（`asset.primary_name` 就这样），真问题反而埋进噪音里。
审计要点：INSERT 写了表里不存在的列 = 硬缺陷；回读值必须 == 入参。

### 第 33 关 枚举兜底语义
行为断言 5 条 + 静态扫 `RANK[...] ?? 0`。
**静态扫必须先整文件剥块注释再逐行**：逐行剥漏掉多行块注释的中间行，
会把"讲解坑的注释"当成坑本身报红 —— 闸门自己制造噪音。

### 探针结论（这些没问题，别再怀疑）
- 库损坏（DROP TABLE asset）→ `listAssets`/`stageProgress` 正确抛 `no such table: asset`，不静默返回空。
- 非法靶标 id → 抛 `engagement not found`；工具层给「没有靶标 X｜现有：…」而非空列表。

## 1.1.117 —— 启动崩溃两根因 + ATT&CK 编号可检索

### 一、宿主启动崩溃：71 条陈旧认证 cookie 撑爆请求头（**宿主侧缺陷，不是插件的**）

现象：双击宿主弹一个框，标题「DeepSeek Harness 无法使用」，主进程活着但 **host 子进程根本不出现**。

排查顺序（这个顺序本身值得记，能省一小时）：
1. 看进程树 —— 有没有 `dsh-desktop-host` 子进程。**没有** = 启动链后半段失败，不是插件加载问题。
2. 崩溃报告在 `%APPDATA%/@deepseek-ai/dsh-desktop/logs/crash-*.log`，`phase: startup`。
   本次报 `Error: desktop welcome: Web authentication failed`（main.js:16856，`connectDesktopWelcome`）。
3. 手工 spawn host 子进程（参数照 main.js 的 `DesktopHostProcess.start()`）+ 直连 URL：
   **303 + set-cookie 全正常** → host 本身健康，问题在 Electron 主进程网络栈。
4. 读 `@deepseek-ai/dsh-client-connection/lib/index.js` 的 `cookieName()`：
   `"dsh-auth-" + base64url(sha256(authority))`，**authority 含随机端口** → 每次启动都是一条新 cookie，旧的永不清理。
5. 读 Chromium cookie 库 `<userData>/Network/Cookies` 的 `cookies` 表 → 71 条 `dsh-auth-*`，全是 127.0.0.1。
6. 逐档构造 Cookie 头实测：60 条 → 14,371B → 401（正常未认证）；71 条 → **16,875B → 431**。
   阈值精确落在 Node `http.maxHeaderSize` = 16384。

修法：每个端口一条都是**一次性**的（token 换 cookie，进程退出即失效），只留最新一条，删其余 70。

**判据沉淀**：401 是「没认证」，431 是「请求头太大」。宿主把两者都归成
`!response.ok` → 同一个 "Web authentication failed"，所以从报错文案**完全看不出**是 header 超限。

### 二、宿主自杀式恢复把 11 个第三方插件全关了（**这个坑最贵**）

致命错误框第三个按钮「禁用第三方插件、备份 profile patch 并重启」→ `disableAllPlugins()` → `sanitizeProfile()`：
- `cordis.patch.yml`（5112B，含 fandai/bendi 自定义模型 + tool-fs 读上限 + dsh-purge autoApplyOnStart）**被 rename 成 `.bak-<ts>` 后写回空 `[]`**；
- `package.json` 的 `dsh.profile.bundles` **从 12 个砍回 2 个**（`WEB_PROFILE.bundles`）—— 11 个第三方 bundle 集体消失。

更要命：那个 rename 出来的备份**可能在同一流程里被后续步骤清掉**。本轮就是：11-13 的旧备份还在，08:03 新备份没了。

**结论：宿主启动失败时先读 crash 报告定位真因，绝不点「禁用第三方插件」** —— 它不修启动，只清空你的配置。

### 判据沉淀（都是本轮撞出来的）
- **「观测项」不是安全的中间态**：只打印不判红的指标，等于承认它不重要。凡是承诺「必须」的
  约束，要么进 problems，要么别写在文档里。9% 挂了多久没人管，就是因为它不进 problems。
- **批量脚本多轮注入会叠加重复行**：表面「表格 8 行很充实」，实际只有 3 条有效信号。
  闸门只看行数会认为合格 —— **重复行挤掉了本该补的观测面**。已加重复行判据。
- **别在有多轮脚本修补的字段上重复叠加**：`competition-supply-chain` 被叠了 3 遍，
  连「实用推论」都串成了 T1078 的（「合法凭据的非法使用」跟供应链无关）。
  改内容要**先读现状再改**，不能假设「上次写的还在原位」。
- **重配内容前先备份已有正确内容**：我第一版按 `s.attack[0]` 配检测表，
  而 attack 是字母序，T1078 常排第一 → cn-oa-exploit（主业 T1190）被配了「账户滥用」的表。
  还覆盖了 11 个**原本就正确**的检测段（credential-attack 的 6 条表被我压成 2 条）。
  修法：先 `git show HEAD:` 把原本有检测段的技能恢复回来，再只补「原无」的。
  **判据：批量改写前必须区分「原本有」与「原本没有」**。
- **闸门判据词表太窄 = 误判**：`SENSE.日志源` 只认 `日志|audit|Sysmon|4624` 时，
  写了「防火墙 / NetFlow」「K8s audit」「WIDS」的段全被判「没有检测点」（误判 27 个）。
  判据的作用是区分「写了具体观测点」与「只写『会有告警』」，不该因为它用了别的日志名就判失败。
- **离线类技能要豁免「两类感知源」**：逆向/固件/取证的动作全在本机，目标侧一条日志都没有。
  强行要求只会逼出编造。改为「诚实说明离线 + 表格够」即合格 ——
  **「目标侧无感」本身就是最有用的结论**。
