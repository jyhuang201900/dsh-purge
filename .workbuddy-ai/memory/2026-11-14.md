## 1.1.98 — 逻辑审阅，修 6 处真实缺陷 + 2 道闸门（`45c11d2`）

1. **回滚与 apply 动作面不对称**：`applyPatchesAllHosts` 默认 `discover:false`，

## 1.1.105 — URL 路径被当成 CIDR，合法目标被误拦（`5a040ef`，tag `v1.1.105-scope`）

### 误拦截：`203.0.113.20/api?id=1` 被范围闸拒
根因 `targetHostOf` 只剥**带协议头**的 URL 路径：
```js
const url = /^[a-z][a-z0-9+.-]*:\/\/([^/?#\s]+)/i.exec(t);
if (url) t = url[1];   ← 无协议的 host/path 没处理
```
于是 host 留成 `203.0.113.20/api?id=1`，`checkTarget` 里判据 `host.includes("/")`
把它当 **CIDR** 送进 `cidrInsideCidr` → 报「该网段未完全落在任何授权网段内」。
→ 修：剥路径时**区分 CIDR 的 `/` 与 URL 路径的 `/`**（真 CIDR 斜杠后只能 0-32 数字）。
→ 关键是**不能放宽范围**：自测同时加正反两类（范围内 host/path 放行、范围外仍拒）。

### 安全组件的错误有两个方向，第二种更隐蔽
- 误放行（把越界的打出去）→ 事故
- **误拦截（把该打的挡住）→ 用户以为工具坏了，然后手动绕过限制**
第二种会**训练出错误习惯**（为了完成任务去改靶域或换写法）。而本次触发条件极日常——
记一个带路径的 URL 而已。

## 1.1.110 — 复现命令自相矛盾（`61dab6b`，tag `v1.1.110-repro`）

### 三个真实缺陷（都在报告正文里看出来的）
① **正文与提示不同源**：正文印 `confirm.replay`（规则里的原始模板，占位符没填），
   提示按 `replay_cmd`（已填充）算 → 「命令里有 4 个占位符，提示说还有 1 个没填」。
   → 正文改用 `replay_cmd`，两边同源。
② **script 模板丢 `<port>`/`<pass>`，且裸 `-p`**：`score-rules.js` 的 `replay` 有、`script` 没有。
   裸 `-p` 在真实 mysql 里是**交互式提示输密码** → 贴进脚本会挂住。
   **它不是"缺字段"，是"看起来能跑但会卡住"**，比缺字段更危险。
③ **占位符填不上**：`templateValues.host` 只认隧道与 `parseTarget(h.target)`；
   target 为空（批量动作/从漏洞反查）时 `<host>` 永远填不上。
   → 加**资产 IP 回落**：隧道可达网段 > 本条 target > 资产 IP。
   → report item 的 `target` 同样回落 `asset_ip`（复现索引「目标」列读它）。

### 闸门判据的关键细节
- **比对占位符「集合」不能比「数量」**：`replay` 与 `script` 两套模板的占位符**个数恰好相同**，
  数数分辨不出正文用的是哪份（实测踩过）。
- 第 28 关 `check-replay-templates`：script 占位符 ⊇ replay 占位符；mysql 不许裸 `-p`。
- 第 27 关扩到 9 项，含两个**独立用例**（模板分支、资产回落），避免"空转通过"。

### 三次探针失效的教训（重要）
前三次探针显示"通过"全是空转，原因各不相同：
  ① 测试里没凭据 → 两边占位符数相同，分不出
  ② 凭据没挂 `asset_id` → trace 是 `WHERE asset_id = ?`，查不到
  ③ 删回落时**把行尾逗号一起删了** → 文件语法错误，测试根本没跑起来
→ **探针显示通过时，先自证它真的改到了代码**（改完打印 diff / 断言文件内容变了）。
→ 反向探针要构造"能分辨"的用例，否则测的是空转。

## 1.1.111 — 否定结果落库，连续性闭环（`10c4196`，tag `v1.1.111-continuity`）

### 缺口：落库的只有成果，没有「试过但没通」
插件前提是「会话一断、上下文一清，只有落库的还在」，实测只兑现一半：
① 失败尝试唯一能塞的地方是 `vuln` 表 → 出现「尝试但失败的SSRF｜low/candidate」，
   污染漏洞统计、还可能被当战果。`VULN_STATUSES` 也没有「打了但没打通」这一类。
② `stages` 只列 5 个阶段名，没有进度。
根因：`attack_step` 有 `result`（原始回显），**没有字段区分成功/失败**。

### 修法
① `attack_step.outcome`（ok/fail/partial）。**独立字段而非 result 前缀**——
   result 是原始回显（报告要保留原文），混进判定就不再是原始材料。
② `migrate()` 加 `ensure('attack_step','outcome','TEXT')` → 老库自动补列。
③ 输入归一化：`ok/success/成功`、`fail/failed/失败/不通`、`partial/部分`；
   认不出来**就不写**（不存乱码让下个会话按"未标注"读）。
④ `summary` 新增「已试过但不通 N 条（别重试，换路子）」——这是连续性最直接的一块。
⑤ `chain_add` 返回值确认「结果=不通（已记入…，下个会话会看到）」。
⑥ 新增 `listAttackSteps(id, {outcome, limit})`。

### 加字段的纪律
- **老库兼容是硬要求**：DDL + `migrate()` 的 `ensure` 必须**同时**改，否则升级即崩。
- 验证法：`ALTER TABLE ... DROP COLUMN` 造老库 → 用新代码重开 → 断言列回来了。
- **枚举类字段要归一化输入**，认不出来就不写；静默存乱码等于让下游按"未标注"处理。

### 一次「假设 API 存在」
写 `listAttackSteps` 时直接调用了**当时并不存在**的方法。
→ 加调用前先 `grep` 一遍方法名是否存在（尤其自己刚写的新逻辑）。

## 1.1.112 — 阶段进度从事实库推导（`f7e86a3`，tag `v1.1.112-stages`）

### 缺口：`op=stages` 只列 5 个阶段名
新会话不知道做到哪、该从哪接手。**连续性最后一块空白。**

### 关键取舍：推导，不让人手填
**不要加 `status` 字段让模型自己声明"我完成了"** —— 它会为显得有进展而提前标完成。
事实库的证据（得分/步骤/资产）不会撒谎。
`stageProgress` 优先级：`done`(有计分命中) > `active`(有攻击步骤，**含失败**) >
`started`(有归属资产) > `pending`。
阶段归属复用 `scoreStageOf()`，**与报告/攻击链同一套**（另写一套 → 面板说第3阶段、报告说第2阶段）。

### 踩到一个逻辑错：next 退回已越过的阶段
第一版取"第一个非 done"。实测 `internet=done / boundary=active` 却建议回 `recon`。
`recon` 未开始而 `internet` 已完成 = recon 是被跳过的前置，**不该回头**。
→ 改成"已越过的不回头"：取**最后触达位置之后**最近的未完成阶段。
→ 通用判据：**流水线类推进，next 要按"最后触达"而非"第一个未完成"取**。

### 两套指引并存必须说明关系
`summary` 同时有进度条（阶段级）与「下一步」（动作级），实测看着矛盾
（进度条「边界突破未开始」vs 下一步「阶段④漏洞利用」——后者是前者的前置动作）。
→ 加一行点明：进度条看阶段位置，下一步是补齐该位置的具体动作，同一件事的不同颗粒度。
→ **凡同一屏出现两种颗粒度的指引，都要一句话交代关系**，否则读者会判断为打架。

### 闸门
第 29 关 3 项 → 8 项：空库全 pending｜有得分=done｜只有失败步骤=active｜next 不许退回。
反向探针（改回"第一个非 done"）→ 两条同时报红。
