本文只记**实测结论**与**判读依据**，不写推测；每条都给出取证方式。

## 2. #12 APPROVAL_ASK_SENTENCE_BYPASS：官方改写了句子

- 事实：0.2.2 两版（`0.2.2-alpha.3` / `0.2.2-rc.1`）的 `dsh-user-approval/lib/index.js` 与 `lib/types/index.js` 里，句子已是
  `Approval prompts are enabled in this session: operations that require approval may ask through the configured answerers; without an available answerer, the request fails closed.`
  而我们的锚点是旧句 `Approval policy: ask. Operations that require approval may ask through…`。
- 归属判定（不是靠眼看）：用旧档对跑一次 `--new 0.2.1-rc.2 --old 0.2.0-rc.2`，#12 是 **`ok`（old 2/2 → new 2/2）** → 说明锚点曾是官方原话，**是 0.2.2 线改的文案**，不是我们写错。
- 处理：按表内既有约定**另开一条 `replacements` 臂**（不是发明 `pattern: [...]` 数组写法——全仓 176 处都是单串，数组只有我自己那一处，且 checker 的解析器不认数组）。
- 副作用（重要）：补臂后状态灯从 `74/76` 变成 **`73/76、1 待清洗`**。原因是本机 `user-approval` 里**同时**存在官方新句（未被改写）与我们的 bypass 文本；此前旧锚点在哪都命中不了，于是"官方改写后那处没打上"被绿灯掩盖。**这是真未清洗点，不是新 bug**。
- 处置选择：**没有代跑 `--apply`**（避免在 YG 未重启时改动正在运行的宿主文件）；下次启动 `autoApplyOnStart` 会自动补上，或手动 `dsh-purge --apply`。

## 3. #67 AGENT_LOOP_MESSAGES_GUARD：桌面 app 目录 ≠ npm 同名版本产物

- 事实：npm 标 `0.2.2-rc.1` 的 `dsh-agent-loop/lib/index.js` 里那段是 **5 个 tab** 缩进；我们成功打补丁的本机文件匹配的是 **4 个 tab** 锚点，且该文件**不含 CRLF**（排除行尾差异）。
- 归属判定：旧档对里 #67 是 **`ok`（1/1 → 1/1）**，说明 4 tab 是历史真实形态；0.2.2 的上游把它重新缩进过。
- 结论：`check-anchors` 头注释里"asar 与 npm 产物只差 region 注释与哈希类名、代码文本一致"这个前提**说满了**——缩进层面可以不同。因此它的 `notInEither` 不能直接等同"补丁失效"，必须配合面外分类与旧档对读。

## 3b. 五条 notInEither 待判全部归因完成（真待判 0）

checker 现在自动分四类（0.2.2 档对实测）：
```
notInEither 18 = 结构性面外 13 + 打后形态 4（#3 #50 #87 #88）+ 空白不同构 1（#67）+ 真待判 0
```
- **#3 SCOPE_INTRO**：锚点是正则 `/These instructions are ACTIVE and MANDATORY for the stated scope\.[\s\S]*?\`/g`，句子是**我们自己注入的 scope 段**（`replace: OFFICIAL_SCOPE + "\`"`）。实测该句在 0.2.0/0.2.1/0.2.2-alpha/0.2.2-rc 四个版本产物里**都不存在（含折叠空白后）** → 打后形态，不是破损。注意它的文本里没有字面 `dsh-purge`，所以靠注入特征串识别；新写注入句若不带特征会落到真待判，这是**有意的保守失败**。
- **#67 AGENT_LOOP_MESSAGES_GUARD**：旧档对里 `ok（1/1→1/1）`；0.2.2 两版精确匹配 false、**折叠空白后 true** → 官方只是把那段重排成 5 tab。同时本机匹配我们的 4 tab 锚点，说明**桌面 `resources/app` 构建与 npm 同名版本产物在空白层面可以不同**，`check-anchors` 的头注释前提据此已修正（见第 5 节）。

## 3c. `overrideStatus` 是恒真式（本轮修）＋ 注入正文体积入档

- **缺陷**：旧实现 `if (normalizeOverride(defaultOverrideText())) return "default"` **完全不看磁盘文件** —— 内置默认非空就永远返回 `default`，是个不看现场的假保证（同一插件里 `syncPromptInjectOnDiskSync` 却对同一文件判 `user_custom`，两边口径相反）。
- **修法**：复用 `isKeepableUserOverride` 作唯一判据，四态化：`default`（与当前默认一致）/ `custom`（用户改过，sync 不覆盖）/ `stale-default`（是我们的旧默认，下次启动会被升级）/ `missing`。实测矩阵：相同→`default`、改过→`custom`、空目录→`missing`、真机→`custom`。
- **用户可见后果**：本机 `~/.dsh/prompt-inject.md` 是 **24,163 字**，当前内置默认 **29,777 字**，且 `override-state.json` 记录的 `seedHash` 与现文件哈希已不一致 → 判为 `custom`，**sync 不会自动升级**：也就是说注入正文停在一份历史默认上，少了 5,614 字的新条款。选择权在用户（接受"这就是我的文件"，或主动重置拿新条款），本次**没有代改文件**。
- **体积入档（并进门禁）**：`check-package` 第 12 项给默认注入正文设预算 **33,000 字**（按实测 29,777 放约 11% 余量，现占 90%）。这是把"不许堆叠"变成机器可查的唯一量化口径——默认注入每长一分，所有会话的固定成本都长一分。反向探针：把预算降到 29,000 立刻 `✗ 默认注入正文 29777 字，超预算`（exit=1）。

## 4. 顺手清掉的三个工具级缺陷（都在本轮实测发现）

1. **包清单过滤过头**：`startsWith("dsh-")` 会把 `pi-ai` 这类官方包整个丢出核对面。
2. **分类代码没处理数组**：`files` 是数组时被 `String()` 糊成一行，导致 4 条被误判"键不在 targetFiles"。
3. **解析器丢正则型锚点**：`pRe` 只匹配字符串字面量，`pattern: /…/flags` 整支被丢，使这些补丁 `patterns` 变空、**被误标 `runtimeBuilt`**。修复后 `runtimeBuilt 11 → 8`、`notInEither 17 → 19`（`#3 #21` 才真正进入检查）、`ok 48 → 49`。正则型锚点规模：**4 条补丁 / 187 支里的 7 支**（id `3 21 73 88`）。

## 5. 一个死键与一个 npm 元数据坑

## 9. 真把 asar 拆了之后：宿主进了运行时，插件自己却认不出宿主

第 153 轮实测（`scripts/asar-switch.cmd`）：09:38:10 起看门进程等宿主，09:39:01 宿主退出 → `app.asar` 改名 `app.asar.disabled`（203MB 未动）→ 重新拉起宿主。此后 `resources` 里 `app.asar` 不在、`app.asar.disabled` 在、`resources/app` 被加载：**第 8 节那条「补丁没进运行时」到此消解**，进程内 `purge_status` 报 `surface desktop`、`74/76 applied`、`0 缺文件`。

拆开之后立刻露出两个新问题，都不是「宿主坏了」，是**插件对形态的假设落空了**：

1. **`findAiBase()` 是循环依赖**：桌面的判据（`aiBaseLooksDesktopInstall`）要先知道 `ai_base` 落在 `resources/app/...` 里；而 `ai_base` 的找法（`findAiBaseDesktop` / `findAiBaseWeb`）又要先知道「面」。普通 node 子进程里两边互相等，双双落空 —— `node bin\dsh-purge.js --status` 报 `surface web｜插件根未找到｜0/76, 76 缺文件`，同一台机器、同一个宿主，进程内却一切正常。
   破法：面判成 web 时**先按桌面探一遍**，命中即 `adoptSurfaceForAiBase()` 把面钉成 desktop；显式 `DSH_SURFACE=web` 时不探头上的桌面安装。同时给 `findAiBaseDesktop(discover)` 开了「枚举正在跑的官方客户端」这条重路径 —— 子进程里 `execPath` 是 `node.exe`，轻路径全落空，不发现就永远找不到。
   实测：无 `DSH_BASE`、无 `DSH_SURFACE` 直接跑 → `surface desktop｜插件根 …\@deepseek-ai｜74/76｜0 缺文件`。

2. **`targetFiles` 从 56 变 57，闸门只会喊「变了」，说不出变的是谁**。查清了：`files` 表声明 60 个键，本构建里有 3 个**没有对应文件**按设计不登记（`agent-instructions-bootstrap` / `user-approval-invariant` / `compaction-instant-client`），60 − 3 = 57，全部落到真实文件。
   数字基线上调到 57，但**只比数字这件事本身就是坑**（「少一个 A、多一个 B」会静默通过）—— 现在 `check-package` 除了数字还钉一份 `TARGETFILE_KEYS_BASELINE` 名单，对不上就点名「多出哪个键 / 少了哪个键」。第 56 条文档里「映射键回到 56」的说法以本节为准：**以名单为准，不再追一个会漂的数字**。

## 10. 顺手清掉的三处「看着像坏了」和一处真占地方的东西

1. **888MB 孤儿备份**：`resources` 下挂着两份 `app.dshpurge-prev-*`（各 444.3MB），而 `app.dshpurge-recover.json` 里记录的 `prev`（`…-1794258746336`）早已不存在且 `prevRestored=true` —— 它们不是回滚锚点，是之后几次 apply 的残骸。
   新增 `scripts/prune-host-leftovers.mjs`：默认**只列不删**，`--apply` 才动手，且永不删 `recover.json` 指的那份；默认再保留**最新一份**（`prev-<ms>` 的 ms 就是新旧，留一份＝花 444MB 买一条「不用解开 asar 的秒回滚」的路），`--keep N` 可调。实测释放 444.3MB。
2. **状态面板的 `✗ shim 目录`**：桌面面根本不用 shim（宿主由 exe 启动），长期挂红只会让人以为有东西没清干净。改成「当前面是 desktop 且 shim 不存在 → `n/a（桌面面不用 shim）` 记 ✓」；**web 面缺 shim 仍然红**，不是无脑洗绿。
3. **`未生效：#80 #88` 没说为什么**：这两条是 `DESIGN_SKIPPED_VERIFIED` 里被程序核对过的「设计内 skipped」（清理型 / 打后形态）。现在这一行会带后缀「全部为设计内：清理型 / 打后形态，见 DESIGN_SKIPPED_VERIFIED」——判据取自那份数据，不是硬编码，清单改了这行自动跟着改。

以上三处改的是**插件自己的代码**，而插件跑在宿主进程里：内存里还是旧模块，所以 `purge_status` 的输出要**下次宿主重启**才变（已用单元渲染验证新行为：`✓ shim 目录: n/a（桌面面不用 shim）`、`未生效：#80 #88（…）（全部为设计内…）`）。

## 11. 一条「没有任何补丁写的标记」把 reapply 和看门脚本一起锁死

第 154 轮：宿主已经靠 `resources/app` 目录跑起来了（第 9 节），但 `applyUpdate()` 报
`ok:false｜error:"文件已更新，但还原并重新应用失败: 清洗没有完成"`，`needsRetry:true`；
直接跑 `lib/reapply-cli.js` 得到 `{"ok":false,"error":"清洗没有完成","reverted":42,"applied":59,"failed":0}` ——
**失败 0 条却判没洗完成**，说明判据不在补丁，而在「怎么算洗过」。

顺藤摸到 `lib/host-clean.js` 的 `hostPromptKeepsInject()`：它要求文件里出现
`[dsh-purge] complete prompt keeps waterfall inject`（或旧写法 `... keeps inject`）才认。
全仓库 grep：**这两条标记只出现在判据本身和 `lib/desktop.js` 内嵌的同一份判据里，没有任何补丁写它们**。
更糟的是兜底分支把 `transformed.sections : [completeSection]` 当「脏」的判据 ——
而这一行正是 0.2.2-rc.1 **原厂** `dsh-system-prompt/lib/index.js:410` 的写法，
拿原厂特征当「没洗过」的证据，结论必然恒 false。

三个后果，一个比一个贵：

1. `reapply.js` 的 clean = `failed.length===0 && (allPatchHostsWritten || hostCleanMarkersPresent)` → 永远 false，
   于是**每次更新都报失败**（`applyUpdate` 的 `needsRetry` 也跟着一直亮）；
2. 同一份判据被内嵌进 `lib/desktop.js` 的看门脚本（`WScript` 版 `hostClean`），
   换装后 `clean === false` 会走到 `WScript.Quit(1)` —— **看门脚本拒绝拉起宿主**，那才是真正的「启动不了」；
3. 判据两份手抄，改一处忘另一处就会一边说洗过、一边说没洗。

修法（单一来源 + 只认「确实洗过」的证据）：

- `lib/host-clean.js` 导出 `HOST_CLEAN_IDENTITY_MARK` / `HOST_CLEAN_KEEPS_MARK` / `HOST_CLEAN_KEEPS_LEGACY` / `HOST_OFFICIAL_IDENTITY`，
  `hostPromptKeepsInject()` 判定顺序改为：空 → false；有 `identity stripped` 标记 → true；有 keeps 标记（兼容旧形态）→ true；
  否则「是本模块且官方身份行已不在」→ true。**删掉 drops 判据**（那是原厂特征）。
- 新增 `hostCleanFnSource()`：看门脚本要的那行 `function hostClean(body){…}` 由它生成，
  `lib/desktop.js` 不再手抄 —— 两份判据从「靠人同步」变成「结构上不可能不同」。
- `scripts/check-package.mjs` 新增第 13 项「清洗判据自测」：钉三种形态（实机已洗 true / 原厂未洗 false / 空 false），
  并断言生成的看门脚本源码里三条关键判据都在、且不含 drops 那行。
  反向探针 `runs/probe-hostclean-regress.mjs`（探针现场把判据退回旧逻辑再还原）实测能报红：
  `✗ 清洗判据自测失败：实机已洗… 期望 true 实得 false`。

实测闭环：同一台宿主、同一份 `app/lib`，改判据后 `node lib/reapply-cli.js` →
`{"ok":true,"error":"","reverted":42,"applied":59,"failed":0}`，`exit 0`；`check-package` 绿项 +1、问题 0；`verify` 十六关全绿。

**教训**：判据里每一条「必须出现 X」都要能指出**是谁写 X**。指不出来，就不是判据，是永远为假的开关；
而永远为假的开关挂在启动路径上，等于给宿主装了个「看心情不启动」的闸。

## 12. 独立审计的 12 条：混合态、显示名当包名、雷达口径（1.1.88）

这一节记的是**外部审计（只读 subagent，基线 HEAD c128d4e）报出的 12 条**怎么落地的：3 Critical / 5 Important / 4 Minor。
十二条里有十条是同一个病：**代码判的形态和真实形态不一致**，而且不一致的那一侧从来不报错。

### 12.1 混合态（Critical C1-C3）——我们自己造出来的崩机

12:55 宿主连崩三次，`dsh desktop host sent an invalid IPC event` at `resources/app/lib/main.js:3824:31`。
根因不是补丁：`app.asar` 与 `resources/app` 同时存在，shell 与 host 子进程来自不同根，首个 IPC 事件不合 schema。
造出这个形态的是**回滚脚本本身**：

| 位置 | 病 | 修 |
| --- | --- | --- |
| `scripts/asar-toggle.mjs` `--on` | 混合态下只有 `parked` 判据 → 打印「没有 app.asar.disabled，无需回滚」`exit 0`，与同脚本 `--status` 的 `exit 5` 打脸 | 先算 hybrid：`asar` 与 `app` 并存时把目录改名 `app.dshpurge-stale-<ts>` 再退 |
| `scripts/asar-switch.ps1` on 模式 | 目录已挪走、改名循环全败后仍打印「什么都没变，宿主可以照常启动」`exit 5` | 失败分支把 stale 放回，并按真实三态（asar / disabled / app / 放回）报 |
| `scripts/asar-switch.ps1` off 模式看门狗 | 回滚只 `parked → app.asar`，不挪 `resources/app` → 再造成混合态，再按该形态重启 | 回滚前先挪目录，再恢复 asar |

护栏：新增 `scripts/check-asar-switch.mjs`（闸门第 15 项，`npm run check:asar`），
**不读源码猜，直接在夹具上真跑**并断言磁盘三态与退出码：
① 混合态 `--on` 必须解混合（目录变 stale、asar 留下、无 .disabled）；② 无回滚点时不动文件；
③ 目录缺 `package.json` 时 `--off` 必须 `exit 6`；④ 正常形态 `--off` 必须改名。
另加测试缝 `DSH_PURGE_TOGGLE_ASSUME_STOPPED=1`（Agent 自己住在宿主进程里，夹具伪造不了「宿主已退出」）。
