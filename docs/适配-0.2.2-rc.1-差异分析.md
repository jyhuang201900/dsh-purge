# 适配 0.2.2-rc.1 差异分析（2026-11-09）

对象：宿主 `0.2.2-rc.1`（EXE FileVersion 与 `resources/app/dsh` runtime 同号，cordis 4.1.0）。
本文只记**实测结论**与**判读依据**，不写推测；每条都给出取证方式。

## 1. 锚点核对第一次完整跑通

`node scripts/check-anchors.mjs --pkg-list .cache/pkg-list.txt`（`--old` 现在自动从 npm `versions` 表推断，实测推出 `0.2.2-alpha.3`）。

- 包清单：asar 全量是 **320 个 `dsh-*` 包（=640 次产物请求）**；改用 `core.targetFiles()` 真正涉及的面，收窄到 **40 个包**，整轮 **5.4 秒**。
- 判定（补臂后）：`{"notInEither":18,"ok":50,"runtimeBuilt":8}`，**`broken = 0`**（没有任何补丁出现"旧版命中、新版全丢"）。
- `notInEither` 的正确读法已写进脚本输出：**结构性面外 13**（桌面壳 `app/lib/main.js` 不在任何 npm 包内、YAML 预设只索引 JS、`pi-ai` 非 `@deepseek-ai/` 包路径）+ **待人工判 5**（`#3 #50 #67 #87 #88`）。

## 2. #12 APPROVAL_ASK_SENTENCE_BYPASS：官方改写了句子

- 事实：0.2.2 两版（`0.2.2-alpha.3` / `0.2.2-rc.1`）的 `dsh-user-approval/lib/index.js` 与 `lib/types/index.js` 里，句子已是
  `Approval prompts are enabled in this session: operations that require approval may ask through the configured answerers; without an available answerer, the request fails closed.`
  而我们的锚点是旧句 `Approval policy: ask. Operations that require approval may ask through…`。
- 归属判定（不是靠眼看）：用旧档对跑一次 `--new 0.2.1-rc.2 --old 0.2.0-rc.2`，#12 是 **`ok`（old 2/2 → new 2/2）** → 说明锚点曾是官方原话，**是 0.2.2 线改的文案**，不是我们写错。
- 处理：按表内既有约定**另开一条 `replacements` 臂**（不是发明 `pattern: [...]` 数组写法——全仓 176 处都是单串，数组只有我自己那一处，且 checker 的解析器不认数组）。
- 副作用（重要）：补臂后状态灯从 `74/76` 变成 **`73/76、1 待清洗`**。原因是本机 `user-approval` 里**同时**存在官方新句（未被改写）与我们的 bypass 文本；此前旧锚点在哪都命中不了，于是"官方改写后那处没打上"被绿灯掩盖。**这是真未清洗点，不是新 bug**。
- 处置选择：**没有代跑 `--apply`**（避免在 YG 未重启时改动正在运行的宿主文件）；下次启动 `autoApplyOnStart` 会自动补上，或手动 `dsh-purge --apply`。

## 3. #67 AGENT_LOOP_MESSAGES_GUARD：桌面 app 目录 ≠ npm 同名版本产物

- 事实：npm 标 `0.2.2-rc.1` 的 `dsh-agent-loop/lib/index.js` 里那段是 **5 个 tab** 缩进；我们成功打补丁的本机文件匹配的是 **4 个 tab** 锚点，且该文件**不含 CRLF**（排除行尾差异）。
- 归属判定：旧档对里 #67 是 **`ok`（1/1 → 1/1）**，说明 4 tab 是历史真实形态；0.2.2 的上游把它重新缩进过。
- 结论：`check-anchors` 头注释里"asar 与 npm 产物只差 region 注释与哈希类名、代码文本一致"这个前提**说满了**——缩进层面可以不同。因此它的 `notInEither` 不能直接等同"补丁失效"，必须配合面外分类与旧档对读。

## 3b. 五条 notInEither 待判全部归因完成（真待判 0）

checker 现在自动分四类（0.2.2 档对实测）：
```
notInEither 18 = 结构性面外 13 + 打后形态 4（#3 #50 #87 #88）+ 空白不同构 1（#67）+ 真待判 0
```
- **#3 SCOPE_INTRO**：锚点是正则 `/These instructions are ACTIVE and MANDATORY for the stated scope\.[\s\S]*?\`/g`，句子是**我们自己注入的 scope 段**（`replace: OFFICIAL_SCOPE + "\`"`）。实测该句在 0.2.0/0.2.1/0.2.2-alpha/0.2.2-rc 四个版本产物里**都不存在（含折叠空白后）** → 打后形态，不是破损。注意它的文本里没有字面 `dsh-purge`，所以靠注入特征串识别；新写注入句若不带特征会落到真待判，这是**有意的保守失败**。
- **#67 AGENT_LOOP_MESSAGES_GUARD**：旧档对里 `ok（1/1→1/1）`；0.2.2 两版精确匹配 false、**折叠空白后 true** → 官方只是把那段重排成 5 tab。同时本机匹配我们的 4 tab 锚点，说明**桌面 `resources/app` 构建与 npm 同名版本产物在空白层面可以不同**，`check-anchors` 的头注释前提据此已修正（见第 5 节）。

## 4. 顺手清掉的三个工具级缺陷（都在本轮实测发现）

1. **包清单过滤过头**：`startsWith("dsh-")` 会把 `pi-ai` 这类官方包整个丢出核对面。
2. **分类代码没处理数组**：`files` 是数组时被 `String()` 糊成一行，导致 4 条被误判"键不在 targetFiles"。
3. **解析器丢正则型锚点**：`pRe` 只匹配字符串字面量，`pattern: /…/flags` 整支被丢，使这些补丁 `patterns` 变空、**被误标 `runtimeBuilt`**。修复后 `runtimeBuilt 11 → 8`、`notInEither 17 → 19`（`#3 #21` 才真正进入检查）、`ok 48 → 49`。正则型锚点规模：**4 条补丁 / 187 支里的 7 支**（id `3 21 73 88`）。

## 5. 一个死键与一个 npm 元数据坑

- `#12` 的 `file` 里 `user-approval-invariant` 在宿主**没有对应包**（`@deepseek-ai/dsh-user-approval-invariant` 不存在，`targetFiles` 映射为 `undefined`）。留着不致误判（markersAny 命中真实文件即算 applied），但它属于"键存在、面无对应"的那类，若将来出现常年 skipped 应先查这种键。
- `@deepseek-ai/dsh-*` 的 `dist-tags.latest` 是 `0.0.1-rc.1` 这类占位，而 `versions` 表里有 40+ 个真版本。**判宿主新版本必须读 versions 表，看 latest 会被骗**（本仓库第 8 轮就被骗过一次，写下过"宿主版本不能靠 npm 判定"的错结论）。

## 6. 下一档要复查什么

- 官方是否再次改写 approval 句子（#12 两臂 + 两 target 都要重跑）；
- `dsh-agent-loop` 的缩进是否继续漂（#67/#87/#88 都在这个包）；
- `runtimeBuilt` 剩余 8 条（`#5 #6 #7 #8 #10 #15 #16 #70`）：文本由常量/模板拼接而来，属该标签本义，但如果哪天真版官方把它们内联成字面量，它们会转成可核对项，届时 `notInEither` 可能变化。
