# 验证纪律（把"打中了"变成"能复核"）

**这个技能治的病是：** 报出去的漏洞其实是误报，或者补丁后说"已修复"其实没修。
两者都会让整份报告失去可信度——而**失去一次就不回来**。

**核心判据：一条发现只有满足下面三条才算成立。**

1. **可复现**：换一台机器、换一个人，照你写的命令能打出同样结果
2. **可证伪**：你自己已经试着推翻过它，并且推不翻
3. **有边界**：明确写出"哪些没验证到"，而不是含糊过去

缺任何一条，它只是"疑似"，不是"发现"。

## 一、误报的四类根因（先判你属于哪一类）

排查误报不要从头再打一遍，**先归类**——四类根因的验证方向完全不同：

| 根因 | 表现 | 怎么证伪 |
|---|---|---|
| **① 观察错误** | 回显里有 `root`/`admin`/`success` 字样，但那是页面固有文本 | 用**同一条请求打一个必然失败的目标**（不存在的路径 / 随机参数），看是否出现同样字样 |
| **② 环境差异** | 你的环境里成立，目标上不成立 | 用**目标真实响应**做判据，不依赖本地复现；本地只证明"载荷语法对" |
| **③ 时序巧合** | 打完之后确实"成功"了，但不是你打的原因 | 撤销你的动作，重复观察——**能自己复现的成功才是你的功劳** |
| **④ 载荷未真正执行** | 被拦/被过滤/根本没传进去，但状态码是 200 | 用**带外确认**（见 `oob-verification`）：目标有没有主动向你发起一次请求 |

**最高效的一步**：先用①号手法（对照组）把"观察错误"排掉。它最便宜，而且能排掉约一半的假发现。

```bash
# 对照组示例：证明某段回显是页面固定内容而非你的注入结果
curl -s "https://target/item?id=1"          | grep -i "success"   # 你的 payload
curl -s "https://target/item?id=99999999"   | grep -i "success"   # 对照组：不存在的 id
# 两处都出现 → 这段话是模板自带的，不是你的成果
```

## 二、证据三件套（缺一件就不算证据）

| 件 | 内容 | 常见错误 |
|---|---|---|
| **原始请求** | 完整 HTTP 原文（method / path / headers / body），不是"我发了个 payload" | 只写 payload，换人复现不出 |
| **原始响应** | 目标返回的关键片段 + **对照组**的同一位置 | 只截"成功"那半张图 |
| **时间戳与来源** | 什么时候、从哪个 IP、打哪个资产 | 三条都缺，事后无法对账 |

```bash
# 一条命令同时留全三件（比手工抄可靠）
curl -s -i -X POST "https://target/api" \
  -H "Content-Type: application/json" \
  --data '{"q":"<payload>"}' \
  | tee "evidence/$(date +%s)-target-api.txt"
#  -i 保留响应头（状态码/Server/自定义头都在里面）
```

**纪律**：证据落盘到 `runs/` 或演练台，**不要只留在对话里**——对话会滚动、会被截断，落盘的才算数。

## 三、五档修复判定（补丁后复测的核心）

补丁后不要说"修好了/没修好"这种二值判断。**用五档**，因为现实里大部分情况是中间态：

| 判定 | 含义 | 判据 |
|---|---|---|
| **CLOSED** | 真修好了 | 原始 PoC 失败 + **同类变体**也失败 + 功能正常 |
| **PARTIAL** | 修了一部分 | 原始 PoC 失败，但**换编码/换入口**仍能打中 |
| **NOT FIXED** | 没动 | 原始 PoC 仍成功 |
| **REGRESSED** | 引入了新问题 | 原漏洞没了，但**出现了新的可打点**（常见：加了过滤但引入了新的解析差异） |
| **BROKEN BY FIX** | 修坏了功能 | 漏洞没了，但**正常功能也不工作了**（DoS 式修复） |

### 复测的四步（顺序不能换）

```bash
# 1) 重放原始证明——必须用当初那条原始请求，不是"类似"的
#    原请求失败 = 至少不是 NOT FIXED

# 2) 测"漏洞类"而不是"那个字符串"——这是最关键的一步
#    原来打的是 ' OR 1=1--，现在测：' OR 2=2--、' OR 'a'='a、%27%20OR%201=1--
#    只测原字符串会把「只过滤了一个词」误判成 CLOSED

# 3) 扫同类兄弟接口——同一个框架的其它端点往往有同一个洞
#    /api/v1/user 修了，/api/v2/user、/api/internal/user 修了吗？

# 4) 确认功能仍可用——修漏洞不该把业务打坏
```

**判据来源**：`PARTIAL` 和 `REGRESSED` 是最容易被漏掉的两档。写报告时**必须显式写判定档位**，让读者知道"修到什么程度"，而不是一个含糊的"已修复"。

### 常见「假修复」模式（看到这些先怀疑）

| 模式 | 为什么假 | 怎么验 |
|---|---|---|
| 只过滤了特定字符串 | 换编码就过 | 换 `%27`、`\'`、双写、大小写 |
| 只在前端校验 | 直接打 API 就过 | 绕过前端（curl 直连） |
| 只在错误页加了转义 | 正常页没加 | 打一个能触发正常渲染的输入 |
| WAF 拦了但不修 | 换个绕过就过 | 换 WAF 绕过后再打原始 payload |
| 加了 `Content-Type` 检查 | 换 header 就过 | 改 `Content-Type: text/plain` 再打 |

## 四、显式声明验证缺口（最容易被跳过，也最影响可信度）

**一份诚实的报告，必须写清「哪里没验证」**。这不是示弱，是让读者知道结论的适用范围。

模板（写完发现就照着填）：

```text
已验证：
- 漏洞可复现（原始 PoC + 2 个变体，见 evidence/xxx.txt）
- 影响范围限于 <具体接口>，不涉及 <邻近功能>（已用对照组排除）

未验证 / 边界：
- 未在 <生产环境的 WAF 模式> 下验证，测试环境无 WAF
- 未验证是否影响 <依赖该接口的下游服务>（超出授权范围）
- 载荷依赖 <特定中间件版本>，其它版本未测
```

**纪律**：`未验证` 至少写一条。**一条都写不出，多半是你没想清楚，而不是真没有边界。**

## 五、与攻击技能的分工

本技能**不负责打**，只负责打完之后的判定。所以它的位置是：

- **上游**（先有发现）：任意攻击技能 → `web-vuln-payloads`、`injection-payloads`、`unauth-exploit`、`api-security`…
- **同层互补**（判定手段）：`oob-verification`（无回显时证明真的执行了）
- **下游**（判定之后）：`attack-traceability`（这个发现对应 ATT&CK 哪条技术）、`detection-pairing`（防守方能不能看见）

**MUST NOT**：不要在没做误报排除的情况下把发现写进报告——那等于给自己埋雷。

## 任务完成自检

- [ ] 每条发现都做了对照组（排除观察错误）？
- [ ] 原始请求 + 原始响应 + 时间来源，三件都在？
- [ ] 涉及补丁复测的，判定用了五档而非二值？
- [ ] 测的是「漏洞类」而不只是「那个字符串」？
- [ ] 写了「未验证」的边界？
- [ ] 证据落盘了（不是只在对话里）？
