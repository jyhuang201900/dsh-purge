# 报告规范：结构、证据、敏感信息、分受众版本

> 被 `ctf-sandbox-orchestrator` 引用。报告的核心不是"写得好看"，而是**每条结论都能被
> 第三方用文档里的步骤复现**。

## 一、五段结构（缺一段就不完整）

```
1. 背景        —— 范围、时间、目标、假设
2. 发现        —— 每条：标题、等级、位置、描述
3. 证据        —— 原始报文/截图/命令输出（可复现）
4. 影响        —— 具体后果，能量化就量化
5. 修复        —— 可执行建议 + 验证方法
```

## 二、单条发现的模板

```markdown
### 发现 1：订单详情越权（BOLA）

**等级**：高（CVSS 3.1: 6.5，AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N）

**位置**：`GET /api/v1/orders/{id}`

**描述**
订单详情接口仅按 `id` 查询，未校验订单归属。任意登录用户可通过枚举 `id`
读取其他用户的订单，含收货地址、手机号、金额。

**前置条件**
- 两个账号：alice（受害者，order 1001）、bob（攻击者）
- bob 的 access token

**复现步骤**
1. alice 登录，访问 `GET /api/v1/orders`，记录自己的订单 `1001`
2. bob 登录取得 token（见附录 A）
3. 用 bob 的 token 请求 alice 的订单：
   ```http
   GET /api/v1/orders/1001 HTTP/1.1
   Host: app.example.com
   Authorization: Bearer <bob_token>
   ```
4. 响应 `200 OK`，body 含 alice 的完整订单

**证据**
- `evidence/bola_1001.txt`：完整请求/响应
- 时间戳：2024-01-15 10:23:41 UTC
- 重复 3 次均成功

**实际响应（节选）**
```json
{"id":1001,"user_id":1001,"user_email":"alice@example.com",
 "total":299.00,"address":"上海市...","phone":"138****1234"}
```

**影响**
任意登录用户可读取任意订单。`id` 为自增整数，估算可枚举全部约 12 万条订单，
含 PII（手机号/地址）。

**修复建议**
1. 在 DAO 层统一加属主过滤：`WHERE id = ? AND user_id = ?`
2. 或在 Controller 层显式校验：`if (order.getUserId() != currentUser.getId()) return 403`
3. **验证方法**：用 bob 的 token 再请求 alice 的订单，应返回 403
```

## 三、证据的可复现要求

| 证据类型 | 必须包含 | 不可接受 |
| --- | --- | --- |
| HTTP | 完整请求行 + 所有头 + body + 响应状态 + 关键响应头 + body | 只有 URL |
| 命令执行 | 完整命令 + 输出 + 执行用户/主机 | 只有输出 |
| 文件读取 | 路径 + 读取方式 + 内容片段 | 只有文件名 |
| 配置错误 | 文件路径 + 关键行 + 上下文 | 只有"配置不当" |
| 时序类 | 时间戳 + 请求序列 + 各步耗时 | 只有"很快" |

```bash
# 生成证据文件的标准做法
mkdir -p evidence
{
  echo "=== REQUEST ==="
  echo "Time: $(date -u +%Y-%m-%dT%H:%M:%SZ)"
  echo "Actor: bob (user_id=1002)"
  curl -s -i https://app.example.com/api/v1/orders/1001 \
    -H "Authorization: Bearer $BOB_TOKEN"
} > evidence/bola_1001.txt
```

**证据的三个纪律**：

1. **原始**：不加工，不截断关键部分
2. **可独立验证**：别人拿到这个文件 + 账号就能复现
3. **有时空坐标**：时间戳、来源 IP、账号

## 四、敏感信息处理

| 类型 | 处理 |
| --- | --- |
| 真实用户 PII | 脱敏（`alice@example.com` → `a***@example.com`；手机 `138****1234`） |
| 密码/hash | **完全不写**（写"已获取 2 个账号的 hash"，不贴值） |
| Token/密钥 | 脱敏前 8 位 + `...`，且注明"已失效" |
| 内网 IP | 可保留（报告受众是内部）；外发版脱敏 |
| 数据库内容 | 只贴证明所需的最小片段（3 行以内） |
| 客户名/业务数据 | 用占位符（`CustomerA`） |

```bash
# 脱敏脚本（报告生成前跑一遍）
python3 - <<'PY'
import re, pathlib
PATTERNS = [
  (r'[\w.+-]+@[\w-]+\.[\w.]+', lambda m: m.group(0)[0] + '***@' + m.group(0).split('@')[1]),
  (r'\b1[3-9]\d{9}\b', lambda m: m.group(0)[:3] + '****' + m.group(0)[-4:]),
  (r'\beyJ[\w-]+\.[\w-]+\.[\w-]+\b', lambda m: m.group(0)[:12] + '...[REDACTED]'),
  (r'\b[A-Fa-f0-9]{32,}\b', lambda m: m.group(0)[:8] + '...[REDACTED]'),
]
out = pathlib.Path('report_redacted.md')
txt = pathlib.Path('report.md').read_text(encoding='utf-8')
for pat, fn in PATTERNS:
    txt = re.sub(pat, fn, txt)
out.write_text(txt, encoding='utf-8')
print('wrote', out)
PY
```

**特别注意**：报告里**永远不要**贴完整的可用凭据。即使是内部报告，也可能被转发。

```markdown
# 执行摘要（示例）

## 总体风险：高

本次测试发现 3 个高危、2 个中危问题。**最严重的是订单系统的越权漏洞**：
任意注册用户可读取全部 12000 名用户的订单信息（含手机号与收货地址）。
该问题已在线验证，可被自动化批量利用。

## 业务影响
- **数据泄露**：约 12000 名用户的 PII 可被批量获取
- **合规风险**：涉及个人信息，可能触发《个人信息保护法》的告知义务
- **品牌风险**：若被利用，可能出现针对收货地址的精准诈骗

## 建议优先修复
1. 【本周】订单/用户接口加属主校验（发现 1、2）
2. 【本月】用户资料接口加字段白名单（发现 3）
3. 【本季度】引入统一的授权中间件，避免逐接口修补

## 投入估算
- 发现 1-2：2 人日（后端）
- 发现 3：1 人日
- 统一授权层：5-8 人日
```

## 六、等级判定（统一标准）

| 等级 | 判据 | 例 |
| --- | --- | --- |
| **严重** | 无需认证即可 RCE / 全量数据泄露 | 未授权 RCE、SQLi 拖全库 |
| **高** | 低权即可越权访问敏感数据 / 提权 | BOLA 读他人 PII、普通用户提权 |
| **中** | 需特定条件 / 影响有限 | 存储型 XSS（仅自己可见）、有限 SSRF |
| **低** | 信息泄露 / 需高成本利用 | 版本泄露、需物理接触 |
| **信息** | 无直接危害 | 安全头缺失 |

```markdown
## 等级判定说明（写在报告里，避免争议）
- 等级基于"实际验证的影响"，不是"理论最大影响"
- 若利用需要特定条件（如需要受害者交互），在描述里明确
- 同一根因的多个入口合并为一条，不重复计数
```

## 八、检测视角（报告本身的安全）

| 风险 | 处理 |
| --- | --- |
| 报告泄露 | 加密传输；按需分发；水印 |
| 凭据泄露 | 不贴完整值；贴了要作废 |
| PII 泄露 | 脱敏 |
| 内网拓扑泄露 | 外发版删除/泛化 |

## 九、常见坑

1. **结论无证据**——"存在 SQL 注入"但没给 payload 和响应。等于没发现。
2. **证据不可独立验证**——只贴响应不贴请求，别人不知道发了什么。
3. **影响写得虚**——"可能造成数据泄露"→ 应写"可读取 12000 用户的手机号与地址"。
4. **修复建议太空**——"加强输入校验"→ 应写"在 `OrderDao.find` 加 userId 参数"。
5. **不脱敏**——报告被转发后造成二次泄露。
6. **等级虚高**——全部标"严重"，客户会失去信任。
7. **同一根因重复计数**——5 个端点同一个 BOLA 缺陷，算 1 条（列出所有端点）。
8. **不写"未验证"**——把猜测写成结论。要明确区分"已验证"与"疑似"。
