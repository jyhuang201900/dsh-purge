# RFID / NFC 克隆判据

被 `bluetooth-wireless-attack` 引用。

> **合规前置**：门禁卡、工牌、支付卡涉及个人身份与金融数据。
> 没有明确书面授权不要碰；授权范围内也只验证「能否读取/克隆」，**不做消费类验证**。

---

## 一、先判频率与卡型（决定后面全部路径）

```bash
# Proxmark3 的第一步：两个频率各扫一次
proxmark3 /dev/ttyACM0
> lf search        # 125 kHz（低频）
> hf search        # 13.56 MHz（高频）
```

| 频率 | 常见卡型 | 典型场景 |
| --- | --- | --- |
| **125 kHz** | EM4100 / EM4200（ID 卡） | 老门禁、小区门禁、停车场 |
| **13.56 MHz** | MIFARE Classic / DESFire / CPU 卡 | 工牌、校园卡、新门禁 |
| 13.56 MHz | NFC（ISO14443-A/B） | 支付、手机模拟 |

**判据**：`lf search` 能出 ID = 125k 卡（几乎必然可克隆）；`hf search` 出 ATQA/SAK = 13.56M 卡。

## 二、五种卡型的能力矩阵

| 卡型 | 加密 | 能否克隆 | 判据（怎么确认） | 克隆后能否刷开 |
| --- | --- | --- | --- | --- |
| **EM4100**（125k） | 无 | **能**（UID 即全部） | `lf search` 读到 ID | **能**（无任何校验） |
| **MIFARE Classic 1K/4K** | Crypto1（已破） | **能** | `hf mf autopwn` 拿到全部扇区密钥 | **能**（扇区内容完全复制） |
| **MIFARE Ultralight** | 部分有密码 | 能（多数） | `hf mf ulread` | 能（除非配了密码） |
| **MIFARE DESFire** | AES/DES 认证 | **难**（只能中继） | `hf mfdes info` 看是否要认证 | 不能（认证基于密钥） |
| **CPU 卡**（PBOC/EMV） | 双向认证 + 动态数据 | **很难**（需侧信道） | 需要专门工具 | 不能 |

**最关键的判据**：**「能读到 UID」≠「能克隆」**。
DESFire 也能读 UID（为了防冲突），但克隆出来刷不开 —— 因为真正的校验在后续的认证环节。

## 三、MIFARE Classic 的完整流程（最常打的一类）

```bash
proxmark3 /dev/ttyACM0

# ① 确认是 M1（看 SAK 与类型）
> hf search
#   输出 "MIFARE Classic 1K" = 是

# ② 自动破全部扇区密钥（darkside/nested/hardnested 自动选）
> hf mf autopwn
#   耗时：1K 卡通常 1-5 分钟；4K 卡更久
#   结果：打印出 16 个扇区（4K 是 40 个）的 A/B 密钥

# ③ dump 出全部内容
> hf mf dump
#   生成 dump 文件（.bin + .json）

# ④ 写入空白卡（UID 卡，即"魔术卡"）
> hf mf cload -f hf-mf-<UID>-dump.bin
#   注意：普通空白卡不能改 UID（扇区 0 的 UID 是出厂固化的）
#   必须用「UID 可写卡」（俗称魔术卡 / gen2 卡）

# ⑤ 验证：用克隆卡重新读，比对 dump
> hf mf dump
```

**判据**：克隆卡 dump 出的扇区内容与原卡**逐字节相同** = 克隆成功。
只比对 UID 是不够的（扇区里的数据才是门禁系统真正校验的东西）。

## 四、门禁系统的三种校验方式（决定克隆是否有用）

| 校验方式 | 原理 | 克隆是否有用 |
| --- | --- | --- |
| **只校验 UID** | 读卡号比对白名单 | 有用（125k 老卡都是这种） |
| **校验 UID + 扇区数据** | 读扇区里的密钥/签名 | 有用（需完整 dump） |
| **校验动态挑战响应** | 读卡器发随机数，卡用密钥算响应 | **没用**（要密钥，不是数据） |

**判据（怎么判断是哪种）**：拿一个克隆卡去试。
刷不开但有反应（读卡器亮灯/响） = 前两种之一但数据不对；
完全没反应 = 频率/协议不对；
刷开了 = 只校验 UID。

## 五、NFC（手机侧）

```text
NFC 门禁（手机模拟卡）的两种模式：
  · 模拟 UID（部分手机支持）：等同于 125k 老卡的克隆
  · HCE（主机卡模拟）：可自己实现协议（需要知道密钥）

判据：手机能模拟出门禁 = 该门禁只校验 UID（低安全性）。
      手机模拟不了 = 有加密校验（正常）。
```

## 六、验伤与风险

**验伤**：克隆卡**真的刷开了一次**（且记录时间与地点）才算成功。
「dump 出来了」只说明能读，不说明能过。

**风险（必须提前说清）**：
1. **克隆卡使用会留痕** —— 门禁系统记录「同一卡号在两地同时出现」是明显的异常告警。
2. **部分系统会锁定异常卡** —— 反复刷失败可能导致原卡被拉黑。
3. **支付卡绝对不能做消费验证** —— 那是真实的资金损失，不是演练。

## 七、常见坑

1. **用普通空白卡写 M1 dump** —— 写不进去，因为扇区 0 的 UID 出厂固化。必须用 UID 可写卡。
2. **只比对 UID 就宣布克隆成功** —— 门禁可能校验扇区数据。要 dump 全比对。
3. **忽略卡片代际** —— M1 有多个硬件版本，部分版本的加密实现有差异（影响 autopwn 成功率）。
4. **在有人使用的门禁上反复试** —— 会被安保注意到，也可能触发告警。
5. **拿 DESFire 当 M1 打** —— autopwn 会失败（DESFire 是 AES），浪费大量时间。
   先 `hf search` 看型号再选路径。
6. **忘记记录授权范围** —— RFID 涉及个人身份，报告里不能写持卡人姓名。
