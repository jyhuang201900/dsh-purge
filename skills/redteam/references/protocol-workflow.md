# 协议逆向工作流：从抓到包到能重放

> 被 `protocol-reverse` 引用。核心是**把不可读的字节流变成可构造的请求**。
> 顺序固定：定边界 → 找长度与校验 → 推状态机 → 重放验证。

## 一、先定边界（这一步错了后面全错）

```bash
# 1) 抓包（保留原始字节，不要用会重新序列化的工具）
tshark -r capture.pcap -Y "tcp.port==9000" -T fields -e data.data > hex.txt
# 或用 tcpdump 存 pcap，再用脚本切

# 2) 判协议类型（文本 vs 二进制 vs 混合）
head -c 64 hex.txt | xxd | head -4
# 可打印 ASCII 占比高 → 文本协议；否则二进制
```

| 特征 | 类型 | 解析策略 |
| --- | --- | --- |
| 全是可打印字符 + 分隔符 | 文本（HTTP 风格 / 类 JSON） | 按分隔符切 |
| 开头有 `\x00\x00` 或固定魔数 | 二进制（TLV / 定长头） | 按魔数分支 |
| 有大量 `\x00` 填充 | 定长结构 + 填充 | 找字段边界 |
| 长度字段与实际长度相关 | 有长度前缀 | 先定长度字段位置 |

## 二、找长度字段与校验和（协议逆向的核心）

```python
# 典型手法：假设某个 2/4 字节位置是长度，验证它是否等于剩余字节数
data = bytes.fromhex("00012048656c6c6f")

for off in range(0, 6):
    for size in (2, 4):
        v = int.from_bytes(data[off:off+size], "big")
        rest = len(data) - (off + size)
        if v == rest:
            print(f"长度字段可能在 offset={off} size={size}（值 {v} = 剩余 {rest}）")
```

**判定技巧**：

- 抓**多个不同长度的请求**，同一个 offset 的值总是等于剩余长度 → 就是长度字段
- 长度可能是**小端**，也可能是**包含/不包含头部**，都要试
- 校验和：改一个字节，看哪个字段跟着变；改两处能推算出算法（累加/CRC/XOR）

## 三、推状态机（什么时候必须应答）

| 现象 | 说明 |
| --- | --- |
| 发送后服务端不回 | 缺握手/缺认证前置 |
| 第一次能通，第二次失败 | 有序列号或一次性 token |
| 换顺序就失败 | 有严格状态机 |
| 空闲一段时间失效 | 有心跳或会话超时 |

**做法**：抓一个**完整成功会话**，按时间排序，逐个回放（从第 1 个请求开始，
依次增加），第一个失败的请求就是状态机缺口。

```bash
# 逐步回放（每加一条看是否还成功）
for i in $(seq 1 10); do
  head -n $i session.txt | xargs ./replay.sh && echo "前 $i 条 OK" || { echo "卡在 $i"; break; }
done
```

## 四、重放验证（唯一的成功判据）

```bash
# 原始字节重放（不要用 curl 之类会改编码的工具）
python3 -c "
import socket
s = socket.create_connection(('TARGET', 9000), timeout=5)
s.sendall(bytes.fromhex('00012048656c6c6f'))
print(s.recv(4096).hex())
"
```

**验伤信号**：

| 证据 | 说明 |
| --- | --- |
| 服务端返回了**与原始抓包相同结构**的响应 | 协议理解正确 |
| 改一个字段后响应按预期变化 | 说明字段语义理解正确（不是瞎蒙） |
| 能构造**原始抓包里没有的合法请求** | 真懂了协议，不只是回放 |

**反例（看起来成功其实是假）**：
- 服务端返回错误码但 TCP 层"成功" —— 协议层失败了
- 重放成功但只因为服务端没校验（不证明你理解了协议）
- 只在原会话里成功，新连接失败 —— 有会话绑定，你只做到了同会话重放

## 五、字段语义推断（从行为反推）

| 方法 | 做法 |
| --- | --- |
| **单字段变异** | 每次只改一个字段，观察响应差异 |
| **边界探测** | 长度/序号字段改成 0、最大值、负值 |
| **类型探测** | 把整数字段填字符串、把枚举报成非法值 |
| **顺序探测** | 交换两个同型字段，看功能是否互换 |

```python
# 单字段变异模板
base = bytearray.fromhex("00012048656c6c6f")
for off in range(len(base)):
    mutated = base[:]
    mutated[off] ^= 0xFF
    resp = send_and_recv(bytes(mutated))
    if resp != send_and_recv(bytes(base)):   # 响应变了 → 这个字节有语义
        print(f"offset {off} 影响响应")
```

## 六、常见坑

1. **用 curl/Postman 重放二进制协议** —— 它们会重新序列化（改 Content-Length、
   加默认头），原始字节全毁。必须用裸 socket。
2. **只看一条包就下结论** —— 长度字段的判定至少要 3 条不同长度的样本。
3. **忽略 TCP 分片** —— 一个逻辑消息可能跨多个 TCP 段，要用 `tcp.stream` 重组后再切。
4. **假设大端** —— x86/ARM 小端环境很多，长度字段常是小端。两种都要试。
5. **忘了序列号/时间戳** —— 有防重放的协议会拒绝完全相同的重放，必须改那个字段。
6. **加密/压缩层没识别** —— 数据看起来随机（熵高）说明有加密或压缩，
   先解决那一层（找密钥/找算法），不要对着密文猜结构。
