# 输出契约：每轮必须交付哪四样

> 被 `js-reverse` 引用。**「做完了」不算结论**——必须给出可复核的四件套。
> 缺任何一样，这一轮就等于没发生（下一轮的人要从零重来）。

## 四件套（每轮必交）

```
1. 结论      一句话说清「这轮搞明白了什么」
2. 证据      能复核的原始材料（请求/响应/回显/代码片段）
3. 复现      一条可复制的命令，跑一遍就能看到同样的东西
4. 未验证    明确列出「哪些还没确认」
```

## 坏例子 vs 好例子

**坏**：

> 已分析完成，sign 参数是 md5 加密的。

问题：哪个文件？什么 salt？怎么验的？改了输入会变吗？全不知道。

**好**：

```
结论：sign = md5(sortedQuery + "&key=8f2a1c")，与时间戳无关
证据：runs/rebuild-app.example.com-sign.md（5 组输入输出对照表）
复现：node sign.js --query "a=1&b=2"
      期望输出 6c4c1d8e...（与抓包 runs/capture-...json 中 expected 一致）
未验证：
  - 未测超长 query（>2048 字符）是否截断
  - 未确认 key 是否按环境变化（测试环境与生产不同）
```

## 三档完成度（必须明确标）

| 档 | 判据 | 标记 |
| --- | --- | --- |
| **验证通过** | 有对照：同输入同输出，且有原始证据 | `[已验证]` |
| **部分验证** | 逻辑清楚但只能跑通一种情况 | `[部分]` + 列出没验的情况 |
| **未验证** | 只有推测/推测性代码 | `[未验证]` + 说明卡在哪 |

**禁止**：把「部分验证」写成「已验证」。这是最容易被自己骗的地方。

## 输出格式（落盘模板）

```markdown
# <目标> <做什么>

## 结论
（一句话）

## 证据
- runs/<file>：<里面是什么>
- 关键片段：
  ```
  <原始请求/响应/回显>
  ```

## 复现
```bash
<一条命令>
```
期望：<具体输出特征>

## 未验证
- <项 1>：<为什么没验 / 需要什么条件>

## 状态
[已验证] / [部分] / [未验证]
```

## 与其他环节的接法

| 环节 | 拿这份契约做什么 |
| --- | --- |
| 演练台落库 | `redteam_vuln_add` 的 `evidence` 字段直接引用「证据」段 |
| 报告 | 只收 `[已验证]` 的项；`[部分]` 单列一节 |
| 下一轮接手 | 从「未验证」开始，不重复已验证的部分 |
| 检测配对 | 「结论」里的技术点对应 ATT&CK 战术 |

## 常见坑

1. **结论写成过程** —— 「先看了 A 再看 B 然后发现 C」是过程，不是结论。
   结论应该是「C 是什么」。
2. **证据不可复核** —— 只说「验证通过了」但没给输入输出，等于没验证。
3. **复现命令是伪代码** —— `<target>` 占位符留着不填，别人跑不了。
4. **隐瞒未验证项** —— 漏报未验证是最贵的错误，因为它会让下游基于错误假设继续推进。
5. **状态标记模糊** —— 「基本可用」「差不多」都不算状态。只有三档。
